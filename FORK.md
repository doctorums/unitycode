# Как форкнуть UnityCode

UnityCode — не сайт, а протокол. Любой может взять его, поднять свой узел и наполнить
своим смыслом. Сетью никто не владеет. На этой странице — всё, что нужно, чтобы
запустить свой портал, **не разорвав связь с другими форками**.

-----

## Что это и из чего состоит

Три страницы-раздела на агентах — это и есть протокольное меню:

- **Спираль** (`petlya.html`) — генератор. Принимает шум человека → рождает резонанс.
- **Паттерн** (`implant.html`) — аналитик. Читает граф → тихое наблюдение о связях и один открытый вопрос.
- **Сеть** (`set.html`) — карта узлов на Leaflet.

Плюс вход (`index.html`) — генеративное интро, и контентные страницы (`materials.html` —
«Материя», `kniga.html` — читалка), которые к протоколу не привязаны и меняются свободно.

Думают и пишут три агента на Cloudflare Workers. Их код лежит в папке `workers/`:

- `workers/unitycode-petlya.js` → Спираль. Движок — **YandexGPT**.
  Контракт: `POST { raw_noise, lang } → { interpretation }`.
- `workers/unitycode-analyze.js` → Паттерн. Движок — **MiMo**.
  Контракт: `POST { scope, nodes, connections?, lang } → { interpretation, scope, count }`.
- `workers/unitycode-write.js` → шлюз записи. Единственный, кто пишет в базу.
  Контракт: `POST { action, token, turnstile, ... } → { ok }`.
  Внутри него — три агента подряд: **Привратник** (сигнал или пустота), **Distill**
  (короткая выжимка для «Материи») и **Связующий** — после успешной записи узла
  фоново ищет резонанс с существующими узлами и сам создаёт связи.

> ⚠️ Файлы в `workers/` — **снимки** задеплоенного кода, опубликованные для форкеров.
> В бою воркеры живут в Cloudflare Dashboard; он и есть источник истины. Если снимок
> разошёлся с продом — прав прод.

База — Supabase. Таблицы: `nodes`, `connections`, `events`, `linker_log`, `analysis_cache`.
Вся схема разом, включая RLS, — в одном файле `schema.sql`.

-----

## Важное про безопасность

- **Браузер в базу не пишет.** Все записи идут через write-воркер, внутри которого
  лежит **секретный** service-ключ Supabase. Ключ живёт только в воркере, в клиент не попадает.
- **RLS включён** прямо в `schema.sql` — анониму оставлено только чтение. Выполнить обязательно,
  иначе твоя база открыта на запись всему миру.
- **Turnstile** (капча Cloudflare, чаще всего невидимая): write-воркер проверяет токен
  плюс ограничивает частоту через KV. Публичный Site Key лежит в клиенте, Secret Key — только в воркере.
- **Публичный ключ Supabase в клиенте — только для чтения.** Это нормально: RLS не даст записать.

-----

## Форк по шагам

**1. Форкни репозиторий** на GitHub и включи Pages (Settings → Pages → Deploy from branch → main).

**2. Подними свою базу Supabase** (free tier):

- выполни **`schema.sql`** целиком в SQL Editor — он создаёт все пять таблиц и сразу включает RLS;
- если позже будешь создавать таблицы вручную — не забудь `NOTIFY pgrst, 'reload schema';`,
  иначе REST API молча перестанет писать в новую таблицу;
- в Settings → API возьми `Project URL`, публичный ключ (`anon`/`publishable` — для чтения)
  и **секретный** service-ключ (для write-воркера; в клиент не вставлять).

**3. Включи Turnstile** в Cloudflare (раздел Turnstile): создай виджет → получишь
Site Key (публичный) и Secret Key.

**4. Подними три воркера** в Cloudflare — скопируй код из папки `workers/`:

- **генератор** (`unitycode-petlya.js`): секрет `YANDEX_API_KEY`, свой `YANDEX_FOLDER_ID` в коде;
- **аналитик** (`unitycode-analyze.js`): секрет `MIMO_API_KEY`; переменная `SUPABASE_URL`,
  секрет `SUPABASE_SERVICE_KEY` (для кэша анализа — без них аналитик работает, но дороже);
- **шлюз записи** (`unitycode-write.js`): секреты `MIMO_API_KEY`, `SUPABASE_SERVICE_KEY`,
  `TURNSTILE_SECRET`, переменная `SUPABASE_URL`, привязка KV `RATE_KV`;
- **в каждом добавь свой домен в `ALLOWED_ORIGINS`** (вверху файла, ищи метку «ФОРКЕР»).

**5. Впиши свои данные в страницы** (точные места помечены комментарием вверху каждого файла):

- адреса воркеров: `WORKER_URL` (генератор), `ANALYZE_URL` (аналитик), `WRITE_WORKER_URL` (запись);
- `SUPABASE_URL` и публичный ключ Supabase (для чтения);
- Turnstile **Site Key**.

**6. Проверь** по порядку: открой воркер в браузере (должен ответить `{"status":"ok"}`) →
открой Спираль, отправь шум → придёт резонанс → на карте создай узел/связь (пишется через
write-воркер). Если ответа нет и в консоли **CORS** — забыл добавить домен в `ALLOWED_ORIGINS` (шаг 4).

-----

## Что можно свободно менять

Всё, что делает портал **твоим** и не задевает других:

тексты всех страниц · переводы (`i18n.js` и файлы вида `имя_<язык>.md`) · цвета и шрифты ·
анимации входа · подписи кнопок (включая названия пунктов меню — «Узор»/«Паттерн»/любое своё
слово, главное не трогать сами файлы, см. ниже) · вид карты · «Материя» и содержимое Книги ·
свои адреса воркеров, домен, ключи.

-----

## Несущая стена — и почему её лучше не двигать

Код открыт, технически переписать можно всё. Но несколько вещей держат твой портал
**совместимым с общей Сетью**. Сломаешь — узел выпадет из консенсуса будущих форков и
перестанет «говорить на одном языке» с другими. Это не запрет — честное предупреждение
о последствии:

1. **Три протокольных пункта меню и имена файлов.** Имена файлов:
   `implant.html` / `petlya.html` / `set.html`. Подписи и стиль меняй как хочешь (у нас
   они называются Паттерн · Спираль · Сеть); набор и имена этих файлов — нет. Так порталы
   узнают друг друга. («Материя» — контентная страница, она вне этого правила.)
1. **Контракты воркеров.**
   Генератор: `{ raw_noise } → { interpretation }`.
   Аналитик: `{ scope, nodes, connections } → { interpretation, scope, count }`, где `scope` ∈ `personal | social | collective`.
   Шлюз записи: `{ action, token, turnstile, ... } → { ok }`.
   Поменяешь формат — твои агенты перестанут стыковаться с чужими.
1. **Схема базы и RLS.** Таблицы `nodes` и `connections`, имена полей (`raw_noise`, `lat`,
   `lng`, `user_token`, `client_id`, `from_node_id`, `to_node_id`, `status`, `created_by`) и
   включённый RLS (запись — только через шлюз). Другая структура → твои узлы не лягут в
   общую карту.
1. **Связующий уже не «будущий» агент — он работает.** Третий шаг внутри write-воркера:
   после записи узла фоново ищет резонанс с существующими и сам создаёт связи
   (`connections.created_by = 'linker'`). Если меняешь его логику в своём форке — делай это
   так, чтобы созданные им связи оставались читаемы другими форками по той же схеме.
   Доктрина Связующего (атрибуция, прозрачность, обратимость, «связи — да, узлы — нет»)
   описана в `CONCEPT.md`.

-----

## Почему так

Если тебе интересно, что **внутри** портала — несущую стену ты не сломаешь: тебе показали,
где она. А кто захочет сломать — форкнется в свою ветку, и это нормально: Сеть просто
не примет несовместимый узел. Без центрального арбитра. Только естественный отбор тех,
кто говорит на одном протоколе.
